A diagnostic assistant that grades its own reasoning

01 — the problemClinical triage, in the language clinicians already use

Triage today: a patient describes symptoms; a clinician forms a differential through adaptive questioning, narrowing in on the most likely explanations while watching for red flags that demand immediate escalation. The constraint is clinician time, not clinical knowledge — there simply aren't enough hours to have that adaptive conversation with every patient before they're seen.

Most consumer symptom checkers that try to fill that gap are static decision trees returning generic information. They don't adapt their questioning turn to turn, and — the part that matters most — almost none publish accuracy against an external benchmark. A user has no way to tell a good one from a bad one.

02 — how it worksThree loops, and where the model actually sits

There's deterministic code on both sides of every model call — retrieval, safety screening, routing, and every schema boundary are plain Python, not prompted behavior. The three loops:

Loop 1
Actor
Conducts the interview. Receives the patient's structured profile, compressed conversation history, and 3 retrieved few-shot exemplars each turn; decides the next question and updates a ranked differential with probabilities. Outputs strict JSON, validated against a locked schema.
Loop 2
Critic
Scores each turn on question quality, differential quality, and reasoning quality — and, for flagged turns, states would_have_asked: the question it believes should have been chosen instead. Runs in production, not only offline (see §6) — an automated QA layer over clinical AI decisions.
Loop 3
Router
After a session ends, classifies urgency (Emergency / Urgent / Soon / Routine) and specialty from the top differential, using a disease-to-specialty map covering 600+ conditions, with an ambiguity handler when the top differential is unclear.
Retrieval
MMR exemplars
Sentence-embedding retrieval over a curated exemplar pool, re-ranked by Maximal Marginal Relevance so the 3 selected examples are relevant and diverse, not three near-duplicates of the same case.
Provider fallback
Multi-provider retry
The doctor and critic models are configured independently (loop1/config.yaml's models.doctor, and the CRITIC_MODEL env var) — deliberately different models, to avoid the critic grading the actor's own outputs with the actor's own biases. Each provider call retries the same model up to 3 times on a 5xx/malformed response before falling through to the next model in that provider's fallback chain, rather than failing the turn outright:
groq/*→ openrouter (3 models)→ groq/qwen (last resort)
gemini/* · cerebras/*→ openrouter/nemotron
This shape wasn't designed up front — it's the direct result of hitting real free-tier limits in practice: Groq's per-model token-per-minute cap, Cerebras's card requirement for new accounts, OpenRouter's daily request cap. See DECISIONS.md for the reasoning behind each infrastructure choice.

n=20 is the planned evaluation size — small, chosen because each case runs the full multi-turn pipeline against a rate-limited free-tier provider. That's stable enough to compare configurations against each other and too small to claim clinical validity on its own. DDxPlus ground truth is independently derived; no code in this repository generated the labels.

05 — concurrencyWhat changed when the persistence layer was rebuilt

v1 stored appointments as a single-row JSON blob, read-modify-write, no locking. v2 replaced it with a relational schema and a database-level unique constraint. Rather than assert this fixed anything, we ran 20 concurrent booking attempts against the same doctor and the same slot, on both.

07 — prior artThis pattern is not novel — what's uncommon is publishing the number

Adaptive, multi-turn AI symptom checking is an established category. Several commercial products do it, some with real clinical backing and validation far larger than 20 cases. The gap DiffDx sits in isn't the interaction pattern — it's publishing measurable accuracy against an independent dataset alongside an ablation showing which architectural choices earned it.

SystemOverlaps with us onPublishes accuracy on an external benchmark
Ada HealthAdaptive multi-turn interview, ranked differentialAda has published peer-reviewed validation studies comparing its assessments to clinician judgement — larger and more rigorous than this project's evaluation

DeploymentManualDocker, Compose, Render (render.yaml)

Deliberately excluded

  • Async SQLAlchemy — the rest of the codebase is sync; mixing concurrency models for no functional gain at this request volume was judged worse than one consistent style.
  • Migrating password hashing to bcrypt — PBKDF2-SHA256 at 200k iterations is a legitimate OWASP-listed choice; the mismatch was a stale doc comment, not a hashing weakness, so the doc was fixed instead of forcing every user through a re-hash migration.
  • Managed Redis (e.g. AWS ElastiCache) — a plain Redis container reached via a URL, same pattern as DATABASE_URL. At this scale, a managed service's HA/failover value doesn't justify a standing AWS bill.
  • Kubernetes, Terraform, microservices — one FastAPI service, one Postgres, one Redis. Splitting further has no scale justification yet and would slow iteration under deadline.
  • Guideline RAG, PII redaction, DPO fine-tuning — the critic's turn-level scoring builds the training data DPO would consume; the fine-tuning step itself is future work, not built yet.
  • SMS OTP — no free-tier SMS provider exists at any real send volume; email OTP (Resend/SMTP) covers registration verification instead.

10 — limitations

  • Not a medical device. Not clinically validated, not regulated, not for use on real patients.
  • n=20 planned evaluation. Small by design — see §4 for why, and for the honest reading of what that number can and can't support.
  • Ephemeral filesystem on the free/starter deployment tier means uploaded files (X-rays, lab results) do not survive a restart — object storage (S3-compatible) is the production path, not yet built.
  • Test coverage is 24 files in loop1/tests/; a larger suite was scoped out under the capstone deadline.
  • The AWS Fargate deployment described in DECISIONS.md ADR 4 is planned, not deployed — actual hosting today is Render and self-hosted Docker Compose.
  • Provider fallback adds latency variance. A turn that exhausts retries on one free-tier model before falling through to the next can take noticeably longer than one that succeeds on the first call — observed directly during development, not simulated.

11 — guidance requestedFor Prakhar, ordered by how much the answer changes what we build next

  1. Is a 20-case evaluation defensible for a prototype,or does the panel expect a larger n even at prototype scale?
  2. Does the critic-as-production-QA framing map onto how clinical AI is actually governed,or is quality assurance handled differently in practice at Deloitte's clients?
  3. Is clinical triage the right demo domain for this panel,or would a clinical-operations use case land better? The architecture — actor, critic, router — is domain-agnostic.
  4. We're mapping to the DPDP Act and EU AI Act's high-risk classification —is there a Deloitte framework we should align our vocabulary with instead?
  5. We report top-1, top-3, and safety recall —which would a healthcare client actually ask for first?

An architectural choice should be justified by an ablation, not by argument.

Explainability means citing why a question was asked, not narrating after the fact.
