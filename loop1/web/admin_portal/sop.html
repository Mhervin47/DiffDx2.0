SOP

Operator runbook for this admin portal — what each status means, and what to do about it.
Health· DSR· Audit· Evidence & Quality· Usage· Users· Accounts

Health panel

index.html's System Health card, health.js, GET /api/admin/health/detail.

API pill
Trigger
You're looking at the health card and wondering what "API: down" would mean.
Meaning
There is no "down" state for this pill — health.py's handler hardcodes "api": "ok" unconditionally in every response it returns, because if you received a response at all, the API answered. A genuinely unreachable API doesn't render a red pill; the whole panel instead shows "Status unavailable — could not reach the health endpoint."
Action
If the panel shows that fallback message instead of pills, that's your actual "API is down" signal — treat it accordingly.
Escalate if
The panel shows "Status unavailable" for more than one polling cycle (30s) — this is patient-facing downtime, page whoever owns the deploy immediately.
Postgres pill: down
Trigger
Postgres pill reads down.
Meaning
The check is a raw SELECT 1 with a 2s timeout, so this means Postgres is genuinely unreachable — identity, appointments, diagnostic sessions, and llm_usage_events are all unavailable. The appointment double-booking guard (a partial unique index, uq_appointments_doctor_slot_active, on appointments(doctor_id, slot_datetime) for non-cancelled rows) is enforced by Postgres itself — it provides no protection while the database is down.
Action
Check DATABASE_URL and the DB host's own status directly; this is not a code-side fix.
Escalate if
Immediately — this is the single highest-severity pill on this panel.
Redis pill: not_configured
Trigger
Redis pill reads not_configured.
Meaning
REDIS_URL is unset. This is the expected steady state in this deployment, not an error — session_store.py's in-memory fallback is handling live sessions. Read it as informational, not actionable, unless this deployment is specifically supposed to have Redis configured right now.
Action
None, if this is the intended deployment state.
Escalate if
This status changes to down (next entry), or a server restart/redeploy is planned while it reads not_configured (see next entry).
Redis pill: down, or a restart is planned while not_configured
Trigger
Redis pill reads down (configured but unreachable) — or any restart/redeploy is planned while it reads not_configured.
Meaning
Every in-progress diagnostic interview is held only in process memory right now. A restart drops those sessions with no resume path — patients mid-interview lose the conversation. This doesn't show up as an error anywhere else on this panel; the app keeps serving new sessions fine, it just can't survive a restart cleanly.
Action
Before restarting/redeploying for any reason in this state, warn whoever is doing the deploy that in-progress sessions will be lost — this is a coordination step, not a code fix.
Escalate if
This state persists for a production deployment expected to run with Redis — file it as a real incident, not a shrug.
OpenRouter pill: ok
Trigger
OpenRouter pill reads ok.
Meaning
OPENROUTER_API_KEY is present. This does not test connectivity — a 30s-polled health check must never make a billable model call, so this is presence-only. A green OpenRouter pill does not mean the critic or the HTTP-429 fallback chain is actually reachable right now.
Action
If critic scores are missing or turns are failing to fall back correctly while this pill shows ok, don't trust the pill — check application logs for provider activity directly (_FALLBACK_CHAIN in llm.py).
Escalate if
Failures are reported and this pill is the only signal you have — that combination ("no live visibility into provider health") is itself worth escalating, separately from the underlying provider issue.
OpenRouter pill: not_configured
Trigger
OpenRouter pill reads not_configured.
Meaning
OPENROUTER_API_KEY is optional (no default, no boot-time requirement — unlike GROQ_API_KEY, see next entry), so seeing this is not contradictory or unusual on its own. It is, however, a real, actionable fact: the critic is disabled, and the HTTP-429 fallback chain has fewer options than it would otherwise.
Action
If this deployment is meant to run the critic, set the key. If it's deliberately running doctor-only, no action needed — but don't read this pill as "everything's fine," it means a real feature is off.
Escalate if
The critic being off wasn't a deliberate decision for this deployment.
Why there's no Groq pill
Trigger
Looking for a Groq status pill and not finding one.
Meaning
GROQ_API_KEY is required at boot with no default (config.py's Settings class) — the app cannot start without it, so a pill for it could only ever read ok on a running instance. It was removed from this panel and replaced with the OpenRouter pill above, which actually carries information (OpenRouter is optional and gates the critic).
Action
None — this is intentional.
Escalate if
N/A.

Data Subject Request console

dsr.html, dsr.py.

About to run a real (non-dry-run) erasure
Trigger
The dry-run checkbox is unchecked and you're about to click erase.
Meaning
This is irreversible. It touches the relational tables directly (users, diagnostic_sessions, session_turns, appointments, message_threads, uploaded_files, plus everything else that cascades off users via ON DELETE CASCADE), the blob store (appointments, messages, session_report:{id}), and two on-disk log locations (logs/sessions/session_{id}.jsonl, logs/final_records/final_{id}.json). It's gated behind ADMIN_PORTAL_ENABLE_DSR_ERASE (returns a clear 501 error until set) specifically because of that blast radius.
Action
Always run dry-run first and read the full inventory it returns before running the real erase. Confirm the target user/patient independently (name + email + account creation date) before proceeding — there is no undo.
Escalate if
ADMIN_PORTAL_ENABLE_DSR_ERASE is not set and you believe it should be — that's a deliberate infrastructure decision, not a bug; get sign-off before changing it, don't just set the env var.
Erase receipt has a non-empty "warnings" field
Trigger
The response from a completed erase includes one or more entries in warnings.
Meaning
The relational transaction (identity deletion + audit pseudonymization) committed successfully, but the best-effort follow-up (blob store and/or on-disk log cleanup) partially failed — true cross-store atomicity isn't achievable with this architecture. A non-empty warnings field means real PHI may still exist outside the database.
Action
Read every entry in warnings, identify exactly which store/file failed to clear, and manually verify and clean it up — this does not happen automatically on retry.
Escalate if
Any warning is present — this is not a "log it and move on" field, it always needs a documented manual follow-up.
Audit entry shows actor_name: "unknown" after an erase
Trigger
An audit row for the erased subject now shows actor_name: "unknown".
Meaning
Expected. The audit trail is never deleted, but the erased user's actor_user_id is deliberately repointed via uuid.uuid5(fixed_namespace, real_id) to a pseudonymous shadow user (empty name) so the foreign key survives without re-identifying anyone. This is the one place in the codebase an audit row is ever mutated after being written — see the Audit section below.
Action
None required for this specific case.
Escalate if
N/A — informational only. Don't confuse with the failed-login case in the Audit section, which produces the identical text for a different reason.

Audit log

audit.html, audit.py.

Reviewing entries with actor_name: "unknown"
Trigger
An entry's actor shows as unknown.
Meaning
Two distinct causes produce this, and the table alone doesn't distinguish them: (1) a failed login attempt — wrong email or wrong password against a real account, both log with no actor — or (2) a pseudonymized entry left behind by a completed DSR erasure (see above).
Action
Cross-check the entry's action type and timestamp — a login_failed action is case (1); anything else near a known DSR erase timestamp is case (2).
Escalate if
A cluster of case-(1) entries against the same or similar emails in a short window — that's a credential-stuffing/brute-force pattern, not routine noise.
Any mutation seemingly needed on an audit row
Trigger
A row looks wrong and someone wants it corrected or removed directly.
Meaning
No row is ever deleted anywhere in this codebase — that part is a hard rule. It is not, however, strictly append-only in the fullest sense: dsr.py's erasure flow performs one narrow, deliberate UPDATE that repoints actor_user_id to a pseudonym during a DSR erase (see above). That's the single sanctioned exception, and it exists for a compliance reason, not for correcting mistakes.
Action
If a row is factually wrong, add a new row documenting the correction; never attempt to patch the old one directly in the database outside the DSR erasure path.
Escalate if
Someone requests direct DB-level editing of an audit row for any reason other than a DSR erasure — that request itself is the thing to flag upward, regardless of the stated reason.

Evidence, AI Quality, Reports

evidence.html, quality.html, reports.html, compare_report.py.

Citing a cost figure from the comparison report externally
Trigger
About to quote actor_critic's cost-per-session figure in a demo, writeup, or stakeholder update.
Meaning
It's doctor-call cost only, sourced from this offline eval harness's own session logs — it excludes critic, compressor, and profile_updater cost. That's a real undercount, not a deliberate scope choice: the doctor and the critic both run on every turn of a real deployed session (web/api_session.py's _fire_critic); this offline report simply hasn't been wired to pull from the live cost source yet.
Action
Never quote this figure as production cost in isolation. For a real per-session cost figure, use the Cost & Usage panel on the Overview page instead — it's sourced live from llm_usage_events and covers doctor, compressor, critic, and closing-turn calls together (see the Usage section below). If you must cite this report's number, attach the undercount caveat every time.
Escalate if
N/A — standing caveat, not an incident.
Citing a significance result (McNemar) from the comparison report
Trigger
About to present a p-value or accuracy delta from the Evidence page as conclusive.
Meaning
Directional only, never confirmatory — regardless of which way the p-value points. The eval-set size is not fixed at any particular number; it's read live from data/ddxplus_eval_set.json (check eval_set_size in the report itself, don't assume a figure from memory), and each individual comparison's McNemar n is further narrowed to only the patients both actor-critic and that specific baseline were actually run on.
Action
Read the report's own n and n_discordant for the specific comparison you're citing rather than quoting a remembered number; present the result as "suggestive," never as proof.
Escalate if
N/A.
Citing safety-recall numbers
Trigger
About to cite the red-flag top-3 recall figure.
Meaning
Rests on the DDXPlus dataset's own severity field by default, not clinician review — unless the report's label_provenance field shows real overrides. Overrides are applied deliberately via red_flag_labels.py --set PATIENT_ID true|false --labeled-by NAME, which is mandatory to supply a labeler name for; a prior automatic pass never clobbers a real override once applied.
Action
Check label_provenance.automatic vs. label_provenance.override before trusting the number — it reports exactly how many labels are automatic vs. a real, named override.
Escalate if
N/A — check the provenance field, then proceed accordingly.
Comparing the comparison-report numbers to what a real patient session actually costs/does
Trigger
Trying to reconcile this offline benchmark with live production behavior.
Meaning
The live web path and the offline CLI harness these numbers come from are not the same pipeline. Live: doctor, compressor, critic (background thread), and the closing-turn call all run and are logged (call_site on each llm_usage_events row) — profile_updater is the one call deliberately disabled in the live web session (rate-limit reasons), a CLI/offline-only path instead. GET /api/admin/usage's own coverage_note field states this exactly, generated fresh in every response.
Action
Trust /api/admin/usage's own coverage_note over any static doc text (including this page) when the two disagree — it reflects the current state of the code, not a point-in-time writeup.
Escalate if
N/A.

Usage & cost tracking

usage.js, GET /api/admin/usage.

Determining which LLM provider actually served a specific request after a suspected 429/fallback event
Trigger
A turn was slow or failed and you suspect the fallback chain rerouted the request to a different provider.
Meaning
This is answerable — model_actual on each llm_usage_events row is populated with the exact model that served that specific call (post-fallback), for every successful call. /api/admin/usage's model_actual_breakdown (all roles blended) and model_actual_breakdown_by_role (doctor/critic/compressor/closing_turn broken out separately) both surface this on the Overview page's Model & Config card, next to each role's configured model.
Action
Check the "actually serving" line next to the relevant role on the Overview page rather than guessing from logs alone. A small number of very old records predate this field (model_actual_unknown in the response) and are excluded from the percentages, not silently folded in.
Escalate if
N/A — this is a working, live signal, not a known gap.

Users

users.html, users_analytics.py.

Citing "abandonment rate" or the user_quit row from Engagement
Trigger
Citing abandonment_rate_pct or the user_quit row of the termination-reason table.
Meaning
termination_reason == "user_quit" is only ever written by the offline/CLI driver (loop1/session.py) — the live web session driver (web/api_session.py) never produces it, only max_turns/safety_stop/confidence_threshold. On a deployment with only live web traffic, this row (and therefore the abandonment rate) will genuinely read 0 — that is an accurate reflection of what the live path can measure today, not a bug in the query.
Action
Don't read a 0% abandonment rate as "no patient has ever quit mid-interview" — read it as "this signal isn't wired up for the live path yet." If abandonment needs to be measured for real users, that's an instrumentation gap in web/api_session.py, not something this page can surface differently.
Escalate if
N/A — known, documented gap, not an incident.
No admin-cancellation series on the Cancellations chart
Trigger
Expecting to see cancellations broken out by admin, not finding it.
Meaning
Appointment.cancelled_by has three real values: "patient" and "patient_reschedule" (written in routers/appointments4.py), and "doctor" (written by DELETE /api/doctor/appointments/{appt_id} in routers/appointments.py — a doctor cancelling an appointment on their own schedule, surfaced as a "Cancel" button on doctor-portal.html). Admins have no cancellation right in this product — there is no admin-facing action anywhere that cancels a patient's appointment — so "admin" is never written and deliberately never charted.
Action
None — this reflects the actual codebase. If an admin-cancellation capability is ever added as a real product requirement, it needs a new write path (and an explicit product decision to grant admins that right) before it can be a new chart series.
Escalate if
N/A — known, deliberate omission, not a gap.
A KPI tile, chart, or table shows a "Demo data" label
Trigger
Any section on this page shows the amber "Demo data — shown until usage is high enough to chart" note.
Meaning
That specific section's backend response came back with data_sufficient: false (too few real rows to chart meaningfully — the exact threshold differs per endpoint, e.g. fewer than 5 total patients+doctors for the snapshot/timeseries, fewer than 5 ended sessions in range for engagement, every retention cohort under 3 patients). The section is rendering the matching mock fixture instead of the real (sparse) response — never a blend of the two. This is a different mechanism from the "could not reach endpoint" sample-data banner used elsewhere in this portal; don't conflate a real outage with this. The Cancellations chart and the Engagement chart additionally get a narrower, chart-only version of this same fallback: even when the section overall is data_sufficient: true, if that one chart's own series are all genuinely zero (e.g. plenty of real session/patient activity but zero cancellations so far), users.js swaps just that chart to the mock fixture and shows its own demo note — the rest of the section stays real.
Action
None required — this clears itself. It's re-evaluated fresh on every poll/fetch, no manual toggle or persisted state; once enough real activity accumulates, the label and demo numbers disappear on the next load.
Escalate if
N/A — unless the label never clears despite genuinely high real usage, which would point to a bug in the threshold check itself.
Comparing doctor and patient counts on the Growth & Activity charts
Trigger
Tempted to read a doctor-count change and a patient-count change as the same kind of growth.
Meaning
Doctors don't sign up — every doctor account is seeded by ops (scripts/seed_doctors.py), never self-registered. A spike in the doctor roster is a roster action, not organic growth, and is never comparable to patient acquisition. The two charts intentionally use separate axes and separate headings for this reason.
Action
Read "New patients vs. active patients" as real organic growth/engagement. Read "Doctor roster + active doctors" as an ops/roster view — a rising line there means someone added doctor accounts, not that doctors are "signing up" faster.
Escalate if
N/A.
Citing "dormant" or a low retention % externally
Trigger
About to describe a patient as having "churned," or cite the retention table as a subscription-renewal metric.
Meaning
Neither concept exists in this system. There is no account deactivation, no soft-delete, no subscription/plan field anywhere in User. "Dormant" here means only: created more than 30 days ago, with zero login events in the last 30 days — it is an inactivity signal, not an account state. "Retention" means only: a second DiagnosticSession or Appointment within 30 days of the first — repeat clinical activity, not a renewal. DSR erasure (a rare, explicit, privacy-driven hard delete) is never counted here as churn, dormancy, or anything else on this page.
Action
Use "dormant" / "at risk" / "inactive," never "churn," when describing these numbers to anyone outside this page — the word choice matters because there is no product concept of a churned account to back it up.
Escalate if
N/A.

Admin account management

scripts/seed_admin.py.

Need to create a new admin account
Trigger
A new admin needs an account.
Meaning
No default admin password exists anywhere in this codebase; ADMIN_SEED_EMAIL and ADMIN_SEED_PASSWORD are both required, and the script refuses to run without both set. It checks for an existing user by email first and skips (does nothing) if one is already there — it does not upsert and does not error on a duplicate.
Action
Run ADMIN_SEED_EMAIL=... ADMIN_SEED_PASSWORD=... PYTHONPATH=src python scripts/seed_admin.py from loop1/, after alembic upgrade head has run. Safe to re-run against an already-seeded email.
Escalate if
N/A — routine operation, no approval gate exists for this one (unlike DSR erasure).
